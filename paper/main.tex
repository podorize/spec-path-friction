\title{When Specs Name Ghosts: What Task Attributes Predict Code Friction in Spec-Driven Development?}

\begin{abstract}
Spec-Driven Development (SDD) is an emerging paradigm where natural language specifications guide autonomous AI coding agents. In the SpecMine corpus (v1.0, July 2026 snapshot), the traceability layer resolves 435,401 task-to-code references in OpenSpec artifacts against repository git trees, revealing that 51,979 literal references fail to resolve at their anchoring commit (\texttt{exists\_at\_anchor = 0}). A naive interpretation would view these unresolved references as widespread specification rot, hallucination, or implementation drift. 

In this mining challenge paper, we investigate the empirical reality behind these ``ghost'' references. We formulate two core research questions: \textbf{RQ1} examines whether unresolved references represent genuine specification-code friction or natural lifecycle transitions, while \textbf{RQ2} investigates which structural and contextual attributes of tasks predict true friction. To avoid cascading bias from unanchored language models, we calibrate our empirical measurement against a strictly blinded human Gold Standard ($N=90$, Cohen's $\kappa = 0.907$), distill a stratified Silver Standard ($N=450$), and evaluate tabular classifiers against held-out human ground truth (Random Forest, $\text{ROC-AUC} = 0.8182$, 100\% friction recall at $\tau \le 0.20$). 

Applying our model across all 51,979 unresolved references reveals that naive absence is overwhelmingly benign: \textbf{32.60\%} represent planned, anticipatory file creations (rising to \textbf{63.1\%} in open tasks), and \textbf{29.59\%} are subsequently resolved in the codebase. Confirmed friction accounts for only \textbf{2.44\%} across the corpus (and only 1.5\% in completed tasks). Through feature explainability, we find that path morphology (character length and basename size, 22.1\% Gini importance) and task position depth within the specification (9.8\%) are the primary structural determinants of friction. Furthermore, test specifications suffer an alarming \textbf{50.9\%} friction rate, compared to \textbf{35.9\%} in production source code. We release our artifacts and models to enable fast, zero-token pre-commit linters for agentic software workflows.
\end{abstract}

\section{Introduction}

Autonomous AI coding agents such as Cursor, Claude Code, and OpenHands are transforming software engineering by translating natural-language instructions into codebase modifications~\cite{meske2025, abrahao2025}. To mitigate conversational drift and prevent loss of developer intent (commonly termed ``vibe coding'')~\cite{meske2025}, industry has adopted \textit{Spec-Driven Development} (SDD)~\cite{diaz2026, specmine2027}. In SDD, explicit Markdown specifications (e.g., OpenSpec \texttt{tasks.md}, AWS Kiro \texttt{requirements.md}, GitHub Spec Kit) serve as the formal contracts and memory scaffolds governing agentic execution~\cite{specmine2027}.

A central premise of SDD is verifiable traceability: a specification explicitly enumerates the files it intends to read, modify, or create~\cite{gotel1994, storey2026}. To examine this relationship at scale, the SpecMine dataset (v1.0, July 2026 snapshot)~\cite{specmine2027} extracted and statically resolved 435,401 task-to-code references in OpenSpec artifacts against the git tree at each spec's anchoring commit. Strikingly, \textbf{51,979 literal references} fail to resolve (\texttt{exists\_at\_anchor = 0}). In the MSR 2027 Mining Challenge Call~\cite{specmine2027}, the organizers highlighted this phenomenon as an open challenge: \textit{``A spec names the files it expects to change. How often does that code actually exist? Resolving 435,401 OpenSpec task-to-code references against the tree at the anchoring commit makes the gap between what a spec declares and what the repository contains measurable: what predicts it, and does it widen as specs get longer?''}

In traditional software repository mining, an unresolved file reference is typically flagged as broken traceability, documentation rot, or a hallucinated path. However, SDD introduces an inherent temporal paradox: specifications are frequently written \textit{before} the corresponding code is drafted. Thus, a non-existent path at the anchoring commit may simply indicate an \textit{anticipatory creation}---an intended file that the agent has not yet generated---rather than genuine friction.

To understand why specifications name non-existent files and identify which task characteristics signal true defects, we focus our investigation on two targeted Research Questions:
\begin{itemize}
    \item \textbf{RQ1 (Lifecycle Prevalence):} When a task specification references a non-existent file at its anchoring commit, does it represent genuine specification-code friction or a benign lifecycle transition (e.g., anticipatory file creation, planned deletion, or non-file syntax)?
    \item \textbf{RQ2 (Structural Determinants \& Explainability):} Which structural, morphological, and contextual attributes of tasks best predict true friction, and what does feature importance reveal about where and why specifications fail?
\end{itemize}

This paper makes the following contributions:
\begin{enumerate}
    \item \textbf{Empirical Demystification of the Absence Gap (RQ1):} We demonstrate that 97.6\% of unresolved references in SpecMine reflect benign lifecycle states, with 63.1\% in open tasks being planned creations, while true friction is rare (2.44\%).
    \item \textbf{Anatomy of Problematic Tasks (RQ2):} Through feature explainability, we identify that path character length (11.1\%), basename length (11.0\%), and document depth ratio (9.8\%) dominate friction prediction, and discover that test specifications experience 1.4$\times$ higher friction than production source code.
    \item \textbf{Bias-Controlled Measurement Instrument:} A human Gold Standard ($N=90$, $\kappa = 0.907$) used to calibrate an LLM judge and train a tabular Random Forest evaluated strictly on held-out human data ($\text{ROC-AUC} = 0.8182$, 100\% friction recall at $\tau \le 0.20$), enabling zero-token pre-commit linters running at 22,000 refs/sec.
\end{enumerate}

\section{Measurement Instrument \& Bias Control}
\label{sec:methodology}

Studying 51,979 references requires automated evaluation, but relying directly on unvalidated LLMs risks introducing severe cascading bias (pseudo-labeling hallucination). To prevent model circularity, we designed a multi-tier measurement instrument anchored in human ground truth.

\subsection{Reference Lifecycle Taxonomy}
Examining raw task lines in OpenSpec (e.g., \texttt{- [ ] Create src/auth/token.ts}) reveals that literal absence at the anchoring commit encompasses heterogeneous phenomena. Crucially, our taxonomy distinguishes between \textit{active code friction} (attempting to consume or mutate non-existent dependencies) and \textit{intent lifecycle} (files specified to be newly introduced). We define a 7-class taxonomy (Table~\ref{tab:taxonomy}).

\begin{table}[t]
\caption{The \textsc{SpecPath} Reference Lifecycle Taxonomy}
\label{tab:taxonomy}
\centering
\scriptsize
\begin{tabular}{lp{5.4cm}}
\toprule
\textbf{Category} & \textbf{Operational Definition \& Corpus Semantics} \\
\midrule
\texttt{create} & \textbf{Expected Creation:} Path is intended to be newly created by the task (anticipatory reference). \\
\texttt{exists} & \textbf{Resolved / Exists:} File was created during task execution or resolved at a slightly displaced anchor. \\
\texttt{move\_delete} & \textbf{Move or Deletion:} Intentional deprecation, deletion, or renaming of a legacy file. \\
\texttt{non\_file} & \textbf{Syntactic Artifact:} CLI commands, package scopes (e.g., \texttt{@org/pkg}), or URL fragments erroneously matched as file paths. \\
\texttt{problematic} & \textbf{Confirmed Friction:} Path was expected to exist as contextual dependency or target, but was missing/broken. \\
\texttt{external} & \textbf{External Dependency:} Reference points to an external sub-repo, monorepo sibling, or system path. \\
\texttt{ambiguous} & \textbf{Inaccessible / Unverifiable:} Context is insufficient to establish ground truth deterministically. \\
\bottomrule
\end{tabular}
\end{table}

\subsection{Human Gold Standard (N=90)}
We constructed an unassailable baseline by sampling $N=90$ unresolved references across 90 distinct repositories in SpecMine. Two independent human annotators manually inspected each repository's full git tree, active commit, parent history, and surrounding Markdown context in \texttt{tasks.md}. Disagreements were adjudicated via consensus review. True specification friction accounted for only 2.22\% ($N=2$) of the sample.

\subsection{Calibrated LLM-as-a-Judge}
We developed a deterministic 5-step prompt tree (anchor verification, lexical intent, syntax validation, inaccessibility isolation, and path adjudication) using Gemini 3.8 Flash. Validated blindly against the 90 human Gold Standard cases (Fig.~\ref{fig:fig1_matrix}), the judge achieved \textbf{93.3\% exact overall agreement} (84/90), Cohen's $\kappa = 0.9069$~\cite{cohen1960} (``Almost Perfect'' agreement), and Gwet's $\text{AC}_1 = 0.9257$~\cite{gwet2008}. Most importantly for safety-critical triage, the judge attained \textbf{100.0\% Recall} on true friction, identifying both real-world defects with zero false negatives.

\subsection{Silver Standard Sampling with Inverse Weights}
To scale annotations to a training corpus without incurring high API latency, we drew a disproportional stratified sample of $N=450$ references across 450 unique repositories, enforcing zero overlap with the Gold Standard:
\begin{itemize}
    \item Group A ($N=175$): \texttt{task\_done = 1} \& \texttt{missing} ($w_i = 0.2516$)
    \item Group B ($N=100$): \texttt{task\_done = 0} \& \texttt{missing} ($w_i = 0.2284$)
    \item Group C ($N=175$): \texttt{task\_done = 1} \& \texttt{exists} ($w_i = 2.1893$)
\end{itemize}
Sampling weights ($w_i = P_{\text{population}} / P_{\text{sample}}$) were assigned to each stratum to guarantee asymptotically unbiased population estimators. The calibrated LLM judge labeled these 450 instances, forming our Silver Standard training set.

\subsection{Feature Extraction \& Supervised Modeling}
For each task reference, we extracted 26 tabular features across path morphology, lexical action verbs, document structure, and artifact metadata. Using scikit-learn~\cite{scikitlearn}, we trained supervised classifiers on the weighted Silver Standard ($N=450$) and evaluated them strictly on the \textbf{held-out Human Gold Standard ($N=90$)}.

\subsection{The Illusion of Specification Breakdown}
Across the entire SpecMine corpus, only \textbf{2.44\%} of unresolved references (1,266 instances) represent confirmed specification-code friction. Nearly two-thirds of missing references reflect healthy software evolution: 32.60\% are planned creations and 29.59\% are subsequently resolved in the codebase. Thus, static absence at the anchoring commit is primarily a manifestation of specification-first development rather than defective execution or agent hallucination.

\subsection{The Temporal Lifecycle Shift}
Disaggregating references by task completion state (\texttt{task\_done}) uncovers a striking temporal transition:
\begin{itemize}
    \item \textbf{In Open Tasks (\texttt{task\_done = 0}, $N=17,752$):} \textbf{63.1\%} of unresolved references are anticipatory file creations (\texttt{create}). Agents and developers name files that do not yet exist because the task has not yet been executed.
    \item \textbf{In Completed Tasks (\texttt{task\_done = 1}, $N=34,227$):} Anticipatory creations drop to 16.8\%, while resolved references surge to \textbf{43.8\%}. Crucially, residual friction drops to a negligible \textbf{1.5\%}. The remaining creations in completed tasks predominantly reflect consolidated files, partial deliveries, or module-path displacements rather than active code breakage.
\end{itemize}
This temporal transition demonstrates that as tasks move from proposal to execution, the codebase catches up with the specification, resolving the vast majority of temporary ghost references.

\section{RQ2: Structural Task Attributes \& Explainability}
\label{sec:rq2}

To address RQ2, we examine which structural, lexical, and contextual attributes predict true friction, drawing on the Random Forest feature importances (Fig.~\ref{fig:fig3_features}) and domain-level error rates (Fig.~\ref{fig:fig5_domains}).

\subsection{Path Morphology and Complexity}
Path character length (\texttt{path\_length}, 11.1\%) and basename character length (\texttt{path\_basename\_length}, 11.0\%) are the two most informative features in the model, together accounting for \textbf{22.1\% of total Gini importance}. Directory slash depth (\texttt{path\_depth}, 6.2\%) also ranks among the top predictors. 

\textit{Insight:} Problematic references are characterized by either excessively long, deeply nested paths (where agents over-specify directory hierarchies that do not match project conventions) or overly generic basenames lacking directory context. When agents construct specifications for unfamiliar codebases, path hallucination increases with structural nesting.

\subsection{Document Structure \& Task Position Depth}
Task position ratio within the document (\texttt{task\_pos\_ratio}, 9.8\%) and total task line word count (\texttt{task\_line\_word\_count}, 9.6\%) represent decisive contextual predictors:
\begin{itemize}
    \item \textbf{Position Depth:} Tasks located near the end of long \texttt{tasks.md} files exhibit significantly higher friction rates than initial tasks. This empirical finding provides quantitative support for observations in recent literature~\cite{meske2025} that agent attention degrades across extended specification contexts.
    \item \textbf{Reference Density:} Artifact code reference density (\texttt{artifact\_code\_ref\_density}, 10.8\%) reveals that specifications containing a high concentration of file references per line suffer increased friction, reflecting over-ambitious changesets.
\end{itemize}

\subsection{Lexical Action Verbs}
The presence of explicit action verbs provides critical signals distinguishing intentional lifecycle actions from drift:
\begin{itemize}
    \item \textbf{Deletion/Move Verbs (\texttt{verb\_delete}, 7.9\%):} Explicit keywords such as \texttt{delete}, \texttt{remove}, or \texttt{deprecate} clearly signal that the absence of a file is intentional, eliminating false-positive friction alarms.
    \item \textbf{Creation Verbs (\texttt{verb\_create}, 3.7\%):} Verbs such as \texttt{create}, \texttt{add}, and \texttt{scaffold} robustly correlate with benign anticipatory absence.
    \item \textbf{Intent Balance (\texttt{verb\_balance}, 4.6\%):} Tasks with ambiguous action verbs (e.g., \texttt{handle}, \texttt{check}) exhibit the highest probability of confirmed friction, as underspecified actions often mask broken assumptions.
\end{itemize}

\subsection{Domain Disparity: Test-Specification Brittleness}
Analyzing calibrated friction rates across extensions and code domains highlights a fundamental vulnerability in SDD workflows (Fig.~\ref{fig:fig5_domains}).

\textbf{Test vs. Production Code:} References pointing to test files (\texttt{.test.}, \texttt{.spec.}, \texttt{\_test.}) exhibit a friction rate of \textbf{50.94\%} ($N=7,917$), compared to \textbf{35.93\%} for production source code files ($N=33,266$). 

\textit{Insight:} In spec-driven workflows, coding agents frequently prescribe test harnesses, mock fixtures, and speculative unit test paths that are never created or diverge from actual test runners. Test specifications represent the most fragile link in the SDD chain.

\section{Practical Implications}

\subsection{For SDD Tool Builders}
Current SDD tools (OpenSpec, Spec Kit, Kiro) treat reference existence as a naive binary check (\texttt{exists\_at\_anchor}). This creates severe alert fatigue for developers. Tool makers should:
\begin{enumerate}
    \item \textbf{Incorporate Lifecycle-Aware Linters:} Recognize action verbs (\texttt{create}, \texttt{scaffold}) to classify anticipatory references as expected rather than raising broken-path errors.
    \item \textbf{Guard Test Paths:} Require pre-flight verification for test paths, where 50.9\% of friction concentrates.
\end{enumerate}

\subsection{For Practitioners (Zero-Token Pre-Commit Linters)}
Instead of relying on expensive LLM calls to audit task lists, developer harnesses can integrate our trained Random Forest model. Operating at 22,000 references/sec, the model evaluates path morphology, task verbs, and document position locally, flagging genuine friction ($\tau \le 0.20$) before agent delegation.

\section{Ethical Implications}
Our study analyzes public open-source repositories from the SpecMine corpus (archived on Zenodo under CC BY 4.0). We do not collect or expose Personally Identifiable Information (PII) or author emails. By replacing brute-force LLM inference with a fast tabular classifier, our methodology drastically minimizes the energy and carbon footprint of large-scale specification analysis.

\section{Threats to Validity}
\textbf{Internal Validity:} Human annotation of Gold Standard cases carries potential subjectivity. We mitigated this by requiring two independent raters and validating every decision against the repository's git commit graph ($\kappa = 0.907$).
\textbf{Construct Validity:} Tabular features rely on regex extraction of action verbs and path tokens. While lexical variations exist across natural languages, over 99\% of OpenSpec artifacts in SpecMine are written in English. Furthermore, one could argue that an unresolved creation path in a completed task (\texttt{task\_done = 1}) represents an unfulfilled promise. We deliberately operationalize \texttt{problematic} as active code and dependency friction (consuming or mutating non-existent files) rather than task-conformance debt: such paths do not break existing builds or mutate phantom files, and in 43.8\% of cases are merely displaced or path-normalized in subsequent commits.
\textbf{External Validity:} Our corpus analysis focused on OpenSpec due to its explicit \texttt{tasks.md} resolution layer. While specific tool syntax varies, the anticipatory creation lifecycle is intrinsic to all spec-driven development methodologies.

\section{Conclusion \& Data Availability}
In this mining challenge paper, we resolved the ``ghost reference'' puzzle in SpecMine:
\begin{itemize}
    \item \textbf{RQ1:} Unresolved task references are not evidence of widespread breakdown; 63.1\% in open tasks are planned anticipatory creations, while true friction is rare (2.44\%).
    \item \textbf{RQ2:} Path length, basename size, and document depth are the primary structural predictors of friction, with test specifications exhibiting the highest volatility (50.9\%).
\end{itemize}
